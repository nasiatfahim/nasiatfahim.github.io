## 1. Deploy

**See `DEPLOY.md` for the full step-by-step.** Short version: rename your GitHub account to
`nasiat`, create a public repo named exactly `nasiatfahim.github.io`, push these files to its
root, and enable Settings → Pages.

## 3. Design system

Everything lives in `assets/site.css` under `:root`. Change a token, the whole site follows.

| Token | Value | Role |
|---|---|---|
| `--paper` | `#F0F2F0` | Cool chart stock. Deliberately not warm cream. |
| `--paper-2` | `#E8EBE9` | Footer ground |
| `--paper-3` | `#DCE1DE` | Image placeholder |
| `--ink` | `#14181A` | Near-black with a blue cast — 15.9:1 |
| `--ink-2` | `#4E585C` | Body / secondary — 6.5:1 |
| `--ink-3` | `#5F6A6D` | De-emphasised — 4.95:1, still WCAG AA for body text |
| `--rule` | `#C9D0CE` | Hairlines |
| `--rule-2` | `#DDE2E0` | Lighter hairlines (between entries) |
| `--signal` | `#0B6357` | Deep viridian. The **only** accent — trace, links, focus, section labels. |

Every foreground/background pair passes WCAG AA in **both** light and dark mode.
The stylesheet is organised in thirteen numbered sections with a table of contents
at the top; the layout primitives you will reuse are `.entry` (gutter + content,
used by every research item, paper and project), `.rows`/`.row` (date / thing /
attribution) and `.cols` (auto-fitting columns).

Two utility hooks worth knowing:

- **`.section.dense`** — tighter vertical rhythm. `cv.html` uses it throughout,
  because a CV wants density and a research page wants air.
- **A `.section-head` with no `.h2`** automatically tightens its own spacing, so a
  label-only head doesn't leave a hole beneath it.

**Type:** Spectral (display + body) and IBM Plex Mono (all labels, nav, metadata, dates).
Two families, no third. Mono carries every piece of structural information — it's the
instrument-label voice, and it's why the page reads as a scientific record rather than a
CV in a nicer font.

Dark mode is automatic via `prefers-color-scheme`. There is no toggle, on purpose — a
toggle is chrome, and the page has one memorable element already.

## 4. Adding content

**A new publication:** open `_tools/_pages_a.py`, copy an existing `<article class="entry">`
block, edit it, then run:

```bash
cd _tools && python3 _pages_a.py && python3 _pages_b.py
```

That regenerates the interior pages with an identical header and footer. `index.html` is
hand-written — edit it directly.

Always keep the **Published** and **Under review** sections visually separate. Mixing them
is the fastest way to lose a reviewer's trust, and it's the most common mistake on
early-career academic sites.

**Each publication entry needs three things** beyond the citation: what you *contributed*,
what the *result* was, and why it *matters*. A reviewer outside your subfield reads the
title and learns nothing; they read "curated 7,318 South Asian events, no comparable public
benchmark existed" and immediately know what kind of researcher you are.

## 6. If you outgrow this

The moment you're adding a paper a month, move to **Jekyll** — GitHub Pages builds it
natively with no GitHub Actions, and `_layouts/default.html` plus a `_data/publications.yml`
file removes the duplicated header entirely. The CSS transfers unchanged. Astro is better
tooling but needs a build pipeline you'd have to maintain; don't take that on until the
content volume justifies it.
